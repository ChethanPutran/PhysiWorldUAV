## B. The data would be physically wrong even if it ran

5. **Wind and drag forces are never applied.** Hummingbird is an articulation, so `sim.drone._view` is an `ArticulationView`. That class has no `apply_forces` or `apply_torques`, and [forces.py:255](src/physiworld_uav/forces/forces.py#L255) guards both calls with `hasattr`, so it silently does nothing.
   - Your "wind" episodes would differ from zero-wind only in the logged wind numbers.
   - The method you want is `drone.base_link.apply_forces_and_torques_at_pos(...)`.
   - OmniDrones already calls that same method inside `apply_action`. On the GPU pipeline a second call in the same step may overwrite the first instead of adding to it. The safest fix is one combined call per step.
   - Test it: hover, apply a constant 1 N sideways force, and check the acceleration is about 1.4 m/s².
6. **The force-model geometry contradicts your own config.** [hummingbird.py:39-48](src/physiworld_uav/forces/hummingbird.py#L39) puts thrust along +Y_B and the rotors in the X-Z plane. `uav_hummingbird.yaml` says the body frame is FLU with z up, and OmniDrones thrusts along +Z_B with rotors in the X-Y plane. The rotor-drag torques are therefore computed about the wrong axes.
7. **Angular velocity is world-frame, but the code treats it as body-frame.** In OmniDrones `get_state()`, `state[10:13]` is world-frame; the RateController itself converts it with `quat_rotate_inverse`.
   - Your force models (`omega_B`), the IMU fallback and the logged `angular_velocity` all treat it as body ω.
   - The thesis defines ω in the body frame, so your training labels would be in the wrong frame.
8. **The outer-loop controller ignores yaw.** [controller_adapter.py:128](src/physiworld_uav/core/controller_adapter.py#L128) maps world-frame acceleration straight to roll/pitch, but initial yaw is sampled from [-π, π].
   - At yaw ≈ π the correction flips sign, so position tracking diverges.
   - Rotate the acceleration by yaw: `pitch = (aₓcosψ + a_y sinψ)/g`, `roll = (aₓsinψ − a_y cosψ)/g`.
   - Thrust is also not divided by cos(tilt), so the drone sags whenever it tilts.
9. **Mass/inertia randomization does nothing to the physics.** `_apply_domain` overwrites `drone.MASS_0` and `INERTIA`, which OmniDrones only keeps as cached reference copies. Changing the real mass needs `base_link.set_masses()` / `set_inertias()` and updating `drone.masses`/`gravity`, as OmniDrones' own `_randomize` does. Meanwhile the metadata records the new mass, so the labels would lie. This matters for your H2 mismatch study.
10. **Rotor state carries over between episodes.** `self.throttle` is a first-order filter state, and `_reset_to_full_state` only resets pose and velocity. Each episode, including every counterfactual sibling, starts with the previous episode's rotor speeds. That breaks the "identical initial state" premise of counterfactual pairs.

## C. The data design doesn't match the thesis

11. **The model-ready dataset is built at 200 Hz, not 20 Hz.** `build_samples` gets the raw high-frequency arrays, not the resampled ones. History H=10 is then 50 ms and the longest horizon (20 steps) is 0.1 s, which is useless for a long-horizon study.
12. **The resampler drops actions.** States have N+1 rows and actions have N, so [resampler.py:204](src/physiworld_uav/data/resampler.py#L204) passes `action` through untouched. The 20 Hz files end up with 200 Hz actions.
    - It also smooths the state channels with filtfilt, which breaks `ṗ = v` consistency, the thing your physics prior relies on.
    - Better approach: run the controller at the model rate (e.g. 20–50 Hz) and hold each action for k physics steps. Then subsample states, and `u_t` is exactly the input applied over [t, t+Δt].
13. **Wind ranges ignore the train/OOD split.** `_generate_interventions` hard-codes steady wind of 2–8 m/s plus gusts of 2–5 m/s, so training data mixes in OOD magnitudes up to ~13 m/s.
    - The thesis needs train |w| ∈ [0, 4] and test (4, 8].
    - It also samples vertical "up"/"down" steady wind at 2–8 m/s, which is unrealistic.
    - `config/wind.yaml` is never used: the example's interventions and trajectory specs are hard-coded constants, so `wind.yaml` and `trajectory.yaml` have no effect.
14. **Only one domain is ever used.** `domains[0]` is always taken, so `n_domains` and the randomized modes do nothing (on top of #9).
15. **`random_action` excitation is fully open-loop.** It holds random thrust and rates for 10–15 s, so most of these episodes will drift or hit the ground and then be discarded. Excitation should be a perturbation on top of closed-loop tracking; [reference_perturbation.py](src/physiworld_uav/excitation/reference_perturbation.py) is still a 2-line stub.

## D. Smaller issues

- The drone is reset twice per episode (lines 379 and 386 of the example).
- In replay mode, `thrust_N` logs the norm of the action vector, which isn't in Newtons.
